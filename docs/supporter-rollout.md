# 期間限定サポーター：運用・検証・本番反映

## この改修の位置づけ

既存のWe育アプリに `/supporter` と `/supporter/manage` を追加する。
別アプリ・別デモ・新しい認証サービス・新しいPDF生成基盤ではない。
SE確認済みの前提：本アプリはLINE・Google・Apple、Web版はLINEのみ。
メール・Guestログインは存在しない。施設はぶどうの木専用Googleアカウントを使う。
ただし照合したWeb側コードにはLINE/LIFFしか存在しない。
サポーター機能は認証プロバイダーを追加せず、認証後の共通ユーザーIDに接続する。
詳細なコード照合結果・操作手順・SE反映条件は `docs/supporter-se-handoff.md` を参照。

## 認証と有効化

- `SUPPORTER_ACCESS_ENABLED=true` のときだけ新機能と厳格な旧API制限が有効になる。
- 本番ではさらに `SUPPORTER_AUTH_MIGRATION_READY=true` が必要。
- フラグは認証や親権限を作成するものではない。値を変えるだけで本番公開しない。
- 通常利用の家族コード・端末の役割・`users.family_id` は親権限の証拠にしない。
- 親権限は確認済み `parent_access`、施設は `supporter_accounts` と実アカウントを紐付ける。
- 施設の招待は登録済みの宛先識別子へ固定する。メール送信・アカウント新規発行は行わない。
- 宛先識別子や施設公開コードは秘密のログイン資格情報ではない。
- 管理者画面で既存ユーザーを施設公開コードに紐付ける。メール本人確認は追加しない。
- 親権限の登録は、管理者による本人・所属確認と明示的な確認理由を必要とする。
- テストの架空アカウントを実在ユーザーや確認済みの施設へ転用しない。

## SEへ確認すること

1. 本アプリのGoogle・Apple認証を含むserver/auth.tsと関連する既存の検証処理、
   アカウント識別子、サーバーセッションへの引き渡し仕様。
   認証情報の値をチャットやドキュメントへ記載しない。
2. `users` は現状LINE ID必須。架空のLINE IDを本番へ作るのではなく、
   既存認証との識別子対応・移行を設計する。
3. 既存ユーザーについて、実際の本人と親権限を確認する移行手順。
   自己申告の「パパ/ママ」や家族コードだけで確認済み行を作らない。
4. 旧アプリ/API利用者への更新・再認証案内と、認証移行の段階的な検証。
   厳格モード有効時はセッションなしの既存API利用を拒否する。
5. 施設管理者、復旧手段、端末紛失時のセッション失効を既存認証に合わせて決める。
   個々の職員識別やアプリ独自の無操作ロックは今回追加しない。

## データ・表示

- 施設アカウント単位で入力者を保持し、表示は登録名（初期値「ぶどうの木」）。
- 個々の職員の入力欄・識別情報は持たない。
- 日常記録は現在有効な招待期間の和集合で共有し、重複表示しない。
- 開始前のアレルギー申告・注意事項だけは明示的な共有例外。
- 子ども不明の既存データは推測で公開しない。
- 施設記録は既存 `logs` に残り、親の履歴でも表示できる。
- 訂正・削除は自アカウントの記録だけ、監査履歴を残して実行する。
- 削除された記録は通常一覧から除外し、監査履歴を通常のAPIへ返さない。
- 既存の一般編集・一括削除から施設記録の履歴を迂回して変更する操作は拒否する。
- 親のポイント・件数による貢献度と、赤ちゃんの健康・日常集計は分ける。
- 過去の記録・ポイント・入力者を推測して書き換えない。

## 通信・期限の制約

- 保存はフォームを開いた時の児童・権限へ固定する。
- 通信断は「通信が切れています。保存できません」と表示する。
- 自動保存・自動再送・通信断のみを理由とする全画面ロックは追加しない。
- サーバーで保存・取得・出力のたびに期間と取消を検証する。
- 通信断中でも既知の終了時刻では表示を終了する。
- 通信断中に新たに行われた取消は即時受信できない。
  復旧後の取得/保存はサーバーが拒否し、画面を消去する。
- 無操作ロックは追加しない。既に見た情報・撮影画像の回収はできない。

## PDF

既存と同じブラウザ印刷/PDF保存方式を利用する。
サーバーの専用出力APIから、権限確認済み・共有対象のみのデータを取得する。
キャッシュ済みの家族全ログやWeBoardを印刷へ渡さない。
新たなサーバーファイルや無認証ダウンロードURLは作らない。
保存・印刷済みPDFは回収できず、院内保管を想定する。
既に開いたOS/ブラウザの印刷ダイアログの操作はアプリから撤回できない。
保管期間・閲覧者・削除手順は運用で別途決める。アプリで勝手に設定しない。

## 開発環境と復元

- 改修前に開発/本番が異なるDBであることを読み取り専用で確認した。
- 初回改修のコード控え：`.local/recovery/supporter-before.bundle`
- SE回答後の改修前コード控え：`.local/recovery/supporter-se-baseline.bundle`
- 説明：`.local/recovery/supporter-baseline.md`
- 開発DBだけに `docs/supporter-development-schema.sql` の追加列・テーブルを適用した。
- 本番DBの既存データ変更・本番公開はこの作業では行わない。
- コード控えはDBバックアップではない。本番のデータバックアップを取得済みとは扱わない。
- 復元はReplitのチェックポイントで対象を確認して行う。
  手動の場合はbundleを別ディレクトリで検証してから復元対象を選ぶ。
- 新テーブルを自動でDROPしない。コードの機能フラグを無効にするだけでは、
  新しい列を参照するコードと古いDBの不整合は解消されない。

## 本番反映の前提・手順

1. SEによる認証経路・親権限移行・施設本人確認を完了する。
2. 本番と分離した環境で、新旧ログイン・親向け全経路・施設権限を検証する。
3. 本番DBのバックアップ/復元手段を別途確認する。
4. Replitの公開時DB差分をレビューし、列/表の追加と既存データ保持を確認する。
   sessionテーブルなどの削除を承認しない。独自の本番起動時DDLは追加しない。
5. Replit側の実装・テスト完了後、SEが本アプリへ反映する。Agentは公開しない。
6. スキーマ・コード・認証設定の組み合わせを確認して段階的に有効化する。
7. 実アカウントで期限/取消/旧API回避不能/親の互換動作を検証してから利用開始する。

## 検証コマンド

- `npm run check`
- `npm run test:supporter`（準備済みの開発DBだけを使用）
- `SUPPORTER_ACCESS_ENABLED=false npm run test:authz`（このテスト子プロセスだけ既存互換モード）
- `npm run build`

API統合テストの本人識別用ヘッダーはテスト内の一時Expressサーバーでのみ使う。
開発環境専用の架空アカウント操作入口は `/supporter/development`。
開発モード・専用フラグ・開発DB名の一致を必須とし、本番は404にする。
指定できるのは固定の架空親/施設だけで、任意の実ユーザーへのなりすましはできない。
本番では専用フラグを設定せず、開発用セッションもサポーター認証に使用できない。
架空ユーザーから通常APIを使う実動作テストと、API応答を模した画面テストを分ける。
いずれも実際のGoogleログインや本番移行の成功を証明するものではない。
