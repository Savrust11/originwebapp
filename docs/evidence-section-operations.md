# 本文区分ごとの適用条件：運用・確認手順

## 今回の範囲

資料のタイトル・著者・発行元・版は引き続き資料全体で管理し、本文区分に
適用条件を持たせます。質問別の回答カード、AI回答生成、大きな管理画面は作りません。
実資料の原文、確認者、確認日時、公開承認を自動設定しません。

既存の開発・本番DBへの適用、実資料本文の登録、Secrets変更、通常アプリの
起動・再起動、AI接続、本番公開は今回の範囲外です。

## 記録を分ける

1. **資料全体**：書誌情報、版、資料全体の条件・制限、採用記録。
2. **本文区分**：原文と出典箇所、対象者、適用年齢、条件と除外条件、
   日本での適用判断、確実性・評価方法・出典箇所、利用条件と例外、限界。
3. **研究対象の説明**：参加者の年齢（範囲と平均は別）、研究実施地域。
   これらはWe育で使える年齢・日本での適用を自動的に決めません。

各項目は次を区別します。

| 状態 | 意味 |
| --- | --- |
| 未確認 | 条件をまだ確定できない。未指定もこの状態 |
| 継承 | 資料全体の指定を使う。資料全体が未確認なら未確認のまま |
| 区分固有 | 当該区分について確認した内容を指定する |

区分固有の指定は、資料全体の除外条件・利用制限を削除する許可ではありません。
制限同士が衝突している場合に区分側を優先して許可することもありません。
利用条件の文章は自動的に法的許可へ変換せず、元の条件と区分の例外を残します。

## 検索時の扱い

- 相談文から対象者・年齢・健康状態を推測せず、明示された検索条件を使います。
- 年齢は子どもの月齢です。保護者本人の年齢と混同しません。
- 明確に適合しない本文区分は結果から除外します。
- 対象・年齢・条件が未確認なら、結果でも未確認と明示します。
- 「分かっている条件」の一覧にないことは、「該当しない」と確認したことには
  なりません。該当すると確認した条件と、該当しないと確認した条件を区別します。
- 年齢だけが適合していても、対象者や他の条件が未確認なら全体を適合済みとして
  表示・利用してはいけません。各項目の判定と元の条件を併せて確認します。
- 結果の件数制限は、区分の適合確認後に適用します。
- 原文、出典箇所、資料・版・本文区分のID、元の条件、実効条件と判定、
  制限・注記を併せて返します。検索結果があることは回答や公開の承認ではありません。
- 新しい条件の構造と入力項目は [実装契約](evidence-section-contract.md) を参照。
- 一回の候補走査は最大2,000区分です。上限に達した場合は
  `diagnostics.reason = "candidate_scan_limit"` を返し、通常の「結果なし」や
  完全な検索結果とは区別します。検索語を絞るか、別途性能設計を見直す必要があります。

## 候補台帳を使う手順

既存の一次選定資料を、引き続き候補台帳として使います。

- 説明資料：`attached_assets/Pasted--We-v0-1-2026-09-17-2-9-11-4-1--1789650057009_1789650057010.txt`
- 候補JSON：`attached_assets/Pasted--title-We-v0-1-checked-at-2026-09-17-status-screening-c_1789650092780.txt`

これらはインポート用完成データではありません。候補IDと本文の採用範囲を
対応付けて検討し、不足情報は不足として残します。台帳の一次確認日を
採用確認日へ転用しません。候補の説明・権利確認メモを保管するために
採用確認処理や公開処理を呼び出してはいけません。

今後実資料を扱うときは、原文・版・対象・採用範囲・利用条件を担当者が
確認した後、別途許可された範囲で登録します。登録・採用確認・公開は別の操作です。
候補台帳から承認状態へ自動変換する機能はありません。

## 将来のDB適用手順（今回は実行しない）

1. 既存DBへの接続・適用許可、バックアップ、影響確認を別途得る。
2. 新規の保存先には初期の `evidence-search-migration.sql`、続いて
   `evidence-section-migration.sql` を適用する。初期SQL適用済みの場合は追加SQLだけ。
3. `db:push` で代用しない。正本SQLの検証関数・公開後の変更禁止も必要。
4. 既存の公開済み本文を継承済み・確認済みに書き換えない。
   条件未登録の本文は保守的に未確認として扱う。
5. 条件を補う場合も公開済み版を上書きせず、新しい版として担当者が確認する。
6. コードと追加SQLを整合させた後、機能の有効化・公開は別途判断する。

## 一時環境での確認方法

環境変数を引き継がない以下の入口だけを使います。
各テストや管理ランチャーを直接起動しません。

```sh
env -i PATH="$PATH" LANG=C LC_ALL=C TZ=UTC \
  node --import tsx tests/run-ephemeral-tests.mjs evidence consultation authz
```

新規作成と所有権を確認した一時PostgreSQLで、ライフサイクル確認後にテストします。
架空資料はTESTと明記し、公開済みの行削除制限を緩めません。
一時環境で使った公開済み資料の後片付けは、所有するクラスター全体の破棄です。
型チェック・ビルドは別途、空にした環境とネットワーク／待受禁止の制限下で行います。
テストとビルドは並行実行しません。

## 残る確認事項

- 実資料の採用範囲・権利・対象者・日本での適用判断は、人による確認が必要です。
- 語句検索は自然文の医学的意味や個別の健康状態を理解するものではありません。
- 利用条件の文章の矛盾や許諾可否を自動で法的に判定するものではありません。
- 架空資料の成功は実際の育児相談での検索品質や医学的正しさを保証しません。
- 公開運用、同意、保存期間、監査、将来のAI回答の安全設計は別の確認事項です。
