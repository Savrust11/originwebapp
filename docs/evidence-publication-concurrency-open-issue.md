# 本番公開前の未解決事項：公開処理と本文更新の競合

**状態：未解決。本番公開前に修正と同時実行テストが必要です。**

今回の非公開相談試作では、この問題の修正や既存DBへの適用は行いません。
通常アプリで公開してよいという判断にも使いません。

## 問題と影響

既存の本文・派生文の更新禁止処理は、資料の版が公開済みかを確認しますが、
その確認時に版の行をロックしていません。

二つの処理が重なると、本文更新側が「まだ下書き」と確認した後で別の処理が
その版を公開し、さらにその後で本文更新が確定する可能性があります。
その間に読む人がいると、同じ版・同じ出典IDなのに異なる本文が見えるおそれが
あります。引用の再現性や、原文・必須文脈を固定して扱う前提に影響します。

必須文脈の**関連付け**には、先の変更で公開処理と順序を合わせる行ロックを
追加しました。しかし、関連付け先の**本文そのもの**と派生文にある既存の
競合まで解決したわけではありません。

## 確認対象

- `docs/evidence-search-migration.sql` の

- 同ファイルの `evidence_derived_texts_immutable_after_publication`
- 比較対象：`docs/evidence-context-migration.sql` の
  `evidence_required_context_immutable_after_publication`

これはコード上の競合分析です。今回、この競合を本番・開発DBで再現していません。
同時実行の再現テストも未実施です。

## 一時環境での再現手順

以下は今後実施する手順です。通常DB、既存のアプリ、実際の公開処理で
試してはいけません。

1. 所有確認済みの新規一時PostgreSQLを作り、専用の未公開テスト版を用意する。
   実資料を使う場合もテスト専用状態とし、人の採用承認を偽って設定しない。
   現在のテスト専用公開シミュレーターの所有確認・マーカー制限を維持する。
2. 同じ一時DBに独立した接続A・Bを作る。時刻や短い待ち時間だけに依存せず、
   実行順を明示的な待ち合わせで制御する。
3. Aでトランザクションを開始し、下書きの本文を更新する。版が未公開であることを
   トリガーが確認し、UPDATEが終了した時点で、Aをコミットせず待機させる。
4. Bで同じ版をテスト専用の公開状態にし、Bをコミットする。
5. 別の読み取り接続で、公開版から見える本文を記録する。
6. Aをコミットし、同じ版・同じ本文IDを再度読み取る。
   版IDが同じまま本文が変われば競合が再現している。
7. 派生文についても同じ実行順を試す。逆順、公開側のロールバック、
   本文更新側のロールバックも確認する。
8. テストが成功しても失敗しても、所有プロセスの停止と一時DB・ファイルの
   削除を確認する。失敗診断には本文、接続情報、セッション情報を出さない。

## 解消の判定条件

- 本文・派生文の変更と版の公開が、版の行ロック等で正しく直列化されること。
- 本文更新が先に確定してから公開されるか、公開が先なら本文更新が拒否されること。
- 公開済み判定だけを外したり、トリガーを無効化したりして解決したことにしない。
- 人による承認、現在版、テスト専用資料の制御を弱めないこと。
- 初期SQLを後から書き換えるだけでなく、追加変更として適用できる形にすること。
- 新規所有一時DBで同時実行回帰テストを通し、既存DBへの適用は別途承認を得ること。
